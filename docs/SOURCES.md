## Cisco FMC Ansible verification

The `fmc-ansible` output pins the official [`cisco.fmcansible` 1.1.1 collection](https://github.com/CiscoDevNet/FMCAnsible/tree/v1.1.1), whose [README](https://github.com/CiscoDevNet/FMCAnsible/blob/v1.1.1/README.md) requires ansible-core ≥2.16 and reports publisher testing with FMC 7.6 and 10.0. Forge's generated output has **not** been tested against a live FMC on either version. Use a controller/Python combination supported by the chosen Ansible release and verify collection compatibility before applying.

Reviewed pinned sources:

- [Usage and HTTPAPI setup](https://github.com/CiscoDevNet/FMCAnsible/blob/v1.1.1/docs/usage.md), [`fmc_configuration` arguments](https://github.com/CiscoDevNet/FMCAnsible/blob/v1.1.1/plugins/modules/fmc_configuration.py) and [configuration implementation](https://github.com/CiscoDevNet/FMCAnsible/blob/v1.1.1/plugins/module_utils/configuration.py): nonempty `filters` use client-side filtering over all pages; single-object creation performs an existing-object comparison, while bulk creation skips it. The generator does not rely on that comparison to establish ownership/order and never requests bulk mode or upsert.
- [`createAccessPolicy`](https://github.com/CiscoDevNet/FMCAnsible/blob/v1.1.1/samples/docs/operations/create_access_policy.md), [`createMultipleAccessRule`](https://github.com/CiscoDevNet/FMCAnsible/blob/v1.1.1/samples/docs/operations/create_multiple_access_rule.md), [`getAllAccessRule`](https://github.com/CiscoDevNet/FMCAnsible/blob/v1.1.1/samples/docs/operations/get_all_access_rule.md), [policy](https://github.com/CiscoDevNet/FMCAnsible/blob/v1.1.1/samples/docs/components/access_policy.md), [rule](https://github.com/CiscoDevNet/FMCAnsible/blob/v1.1.1/samples/docs/components/access_rule.md), [rule metadata](https://github.com/CiscoDevNet/FMCAnsible/blob/v1.1.1/samples/docs/components/access_rule_metadata.md), and [base port literal](https://github.com/CiscoDevNet/FMCAnsible/blob/v1.1.1/samples/docs/components/i_base_port_literal.md): explicit domain/container UUIDs, enabled/action/matcher/logging fields, expanded reads and `section: default`. Optional insertion indices are numeric rule positions, not UUIDs; the generator instead appends one rule per request.
- The matching-major official Cisco provider [2.6.0 destination-port literal schema](https://github.com/CiscoDevNet/terraform-provider-fmc/blob/v2.6.0/docs/resources/access_rule.md#nested-schema-for-destination_port_literals) and [API serializer](https://github.com/CiscoDevNet/terraform-provider-fmc/blob/v2.6.0/internal/provider/model_fmc_access_rule.go) establish `PortLiteral` / `ICMPv4PortLiteral` with required type/protocol and optional port / ICMP type/code. The serializer omits unset `port`, `icmpType` and `code`; the generated protocol-only TCP/UDP and all-type/code ICMPv4 literals follow that shape. This is source/schema review, not proof of acceptance or normalization on a live endpoint.
- [Cisco 7.6 access-control rule guide](https://www.cisco.com/c/en/us/td/docs/security/secure-firewall/management-center/device-config/760/management-center-device-config-76/access-rules.html): ascending rule numbers, first-match behavior, inheritance, zones, native disabled state and start-of-connection logging in the blocking example. The [collection logging example](https://github.com/CiscoDevNet/FMCAnsible/blob/v1.1.1/samples/fmc_configuration/access_rule_with_logging_create.yml) uses `logEnd: true`, `logBegin: false` and `sendEventsToFMC: true` for ALLOW.

The lifecycle deliberately supports dedicated BLOCK-default policy creation and identical-prefix trailing append only. Policy/rule guards reject changes, nonempty unmanaged fields, inherited/read-only objects, non-Default sections/categories and unknown response shapes before writes. API display metadata is ignored only for named object IDs; literal structures are compared strictly. API-normalized defaults may therefore stop a repeat rather than be silently ignored. After writes, full policy and rule reads verify policy identity/ownership, the plain BLOCK default, rule names, positive API evaluation indices, enabled state, actions, matchers, descriptions and logging again; a mismatch requires manual inspection of the partial undeployed policy. No device assignment or deployment is generated. Check mode cannot validate creation-dependent guards and is explicitly rejected. Exclusivity and post-run manual review remain necessary because the API calls are not atomic.

Validation performed:

- All 686 application tests passed, including target/format selection, serialization, native disabled state, strict input guards and generated lifecycle checks. Production build passed; lint passed with the pre-existing React `use-memo` warning in `src/App.tsx`.
- Four generated fixtures (sample, all-disabled, custom ports/zones/references and inert Jinja-looking input) passed YAML parsing, installed native-module argument-name inspection and `ansible-playbook --syntax-check` with `cisco.fmcansible` 1.1.1. This checks playbook syntax/module option names, **not** the full FMC endpoint payload schema.
- 34 scenarios executed the generated assertions/loops with real ansible-core **2.21.6**, Python **3.14.0**, Jinja **3.1.6**, PyYAML **6.0.3**, `ansible.netcommon` **8.7.1** and `ansible.utils` **6.1.1**. FMC module calls were replaced with local facts: creation, identical reapplication, trailing append, all-disabled rules, references and inert user text passed; policy/rule conflicts, unknown sections/categories, invalid indices, check mode and missing/invalid domain stopped before mocked writes. Final action/default conflicts were detected after mocked writes. No HTTPAPI/FMC connection was made.
- Earlier preliminary checks used core 2.16.14 on Python 3.14, which is outside that core release's supported controller-Python matrix; they are not compatibility evidence. The final core 2.21/Python 3.14 combination follows the official [Ansible maintenance/support matrix](https://docs.ansible.com/projects/ansible/latest/reference_appendices/release_and_maintenance.html#ansible-core-support-matrix). The collection's ≥2.16 minimum does not recommend an end-of-life controller.

Remaining live-lab gaps: FMC-version-specific API operation availability, policy defaults, `Default` / `--Undefined--` rule metadata, protocol/ICMP literal acceptance and response normalization, logging behavior, repeated/partial-prefix application and concurrency. Unexpected nonempty fields or missing rule section/category metadata fail closed rather than adopting unknown behavior. No live endpoint-schema, packet, device assignment or deployment verification was performed.
